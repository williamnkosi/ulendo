# Ulendo shared trip contract v1

Status: policy-approved v1 implementation target, not implemented. User approved P01–P11, R01–R15 and O01–O06 with names/coverage deferred as pilot blockers. Whole-contract review and implementation/pilot gates are separate; this document authorizes no implementation, merge, deployment or activation.
Original lineage base: `dc0dd83662244ed543eeb5173451c154cdc8cf16`. Publication checkout base: `cb660ca615e9bb04a47cde77de0252bac72b2023` on main, unchanged. Scope: one reliable trip across rider, driver, and Firebase; no payments, ratings, or pricing.

## 1. Identities and invariants

- `rideId`: backend-generated opaque immutable identifier for one trip, never a rider UID or active-record key alias. `tripId` is not a wire alias.
- `riderId`, `driverId`: authenticated account UIDs. Actor identity comes from authentication, never a trusted client field.
- `offerId`: backend-generated identity for one invitation of one driver to one ride. A subsequent attempt always has a new offerId.
- `commandId`: client-generated UUIDv7 per intended action, persisted before sending and reused across transport retries. Distinct actions use distinct IDs. Backend jobs use deterministic operation IDs.
- `schemaVersion: 1`: wire structure version. `version`: monotonically increasing integer per ride aggregate, starting at 1; not a timestamp or offer ID.
- One rider has at most one nonterminal ride. One driver has at most one live offer reservation or accepted ride. One ride has at most one pending offer. Across roles, one UID has at most one nonterminal rider trip OR driver reservation/accepted assignment, never both. Accounts may use both apps sequentially; login and online intent alone do not occupy this slot. Self-matching (`riderId == driverId`) is forbidden. These C01 policy choices are user-approved in section 10. Immutable participants/locations cannot be reassigned through ordinary commands.
- Backend alone mutates trip, offer, assignment, lifecycle timestamps, and history. Client location/connection events do not change lifecycle.

## 2. Authoritative storage and atomic boundary

Preserve RTDB for live state and Firestore for immutable terminal history. The v1 paths deliberately replace legacy `active_rides/{riderUid}`:

```text
RTDB /trip_state
  rides/{rideId}                         TripSnapshot including pending-offer reference
  riderActive/{riderId}                  {rideId}
  driverControl/{driverId}               {onlineIntent, eligible, onlineRevision, onlineChangedAt?}; server-owned control (5c)
  driverAssignment/{driverId}            {rideId, offerId?, kind: reserved|on_trip}
  offers/{offerId}                       OfferSnapshot
  driverCurrentOffer/{driverId}          {rideId, offerId}
  lastTerminal/{uid}/{role}              {rideId, version, endedAt}
  commandReceipts/{uid}/{commandId}      operation fingerprint + original result
  work/{workId}                         durable dispatch/archive/notification intent
RTDB /driver_presence/{driverId}         server-only telemetry/session fencing and private token (5b)
RTDB /trip_locations/{rideId}            participant-safe assigned-driver location projection
Firestore /rides/{rideId}                terminal TripSnapshot
```

All authoritative lifecycle commands use one Admin SDK transaction at `/trip_state`. Ride, relevant pointers, offer, assignment, successful receipt, and work intent commit together or not at all. Matching first reads presence/candidates outside the transaction, then transactionally claims only a still-unassigned driver whose driverControl is eligible and online, and a still-searching ride. Recheck sampled presence age against backend time on every transaction attempt. Presence freshness/distance are advisory: a disconnect/location change can race a claim, so an offer may reach a recently disconnected/moved driver; expiry/rejection safely releases it. Exclusivity comes from driverAssignment. No separate check-then-set or multi-path update alone substitutes for conditional atomicity.

This is a concrete MVP correctness design with a shared transaction contention boundary, not a scalable final partition design. Do not put GPS data in trip_state; prune terminal data/closed offers/receipts by policy. Backend agreement is conditional on an implementation-stage state-size/contention benchmark and admission limits; no supported production capacity is claimed. Prune finished work and bound candidate scans. If bounded rolling state does not fit the benchmark, redesign partitioning before release, preserving atomicity. Never imply cross-database atomic commits. External notifications/archive writes are durable work performed after commit and retried idempotently.

Driver effective availability is derived in order: offline if ineligible, onlineIntent is false, either telemetry freshness predicate in section 5b fails, or riderActive occupies the UID; otherwise reserved/on_trip when driverAssignment exists; otherwise available. Assignment is always restored separately even when availability reads offline. Inconsistent pointers return reconciliation_required, not guessed availability (section 5a). Only setDriverOnlineV1 changes onlineIntent; trusted administrative code alone changes eligibility. Both controls are checked inside the reservation transaction. Offline-first prevents a new offer; offer-first is withdrawn by the offline command. Heartbeat loss is advisory and cannot directly erase assignment. Going offline while on_trip preserves the ride and assignment. New offers also require a fresh telemetry sample.

## 3. Snapshot wire shapes

All times are backend-authored UTC epoch milliseconds (integers); all coordinates finite numeric WGS84 lat [-90,90], lng [-180,180]. Zero is valid. JSON uses named coordinates, never ambiguous coordinate arrays. Addresses are trimmed nonempty strings, maximum 500 characters. Optional fields may be absent; readers normalize absence to null; RTDB null deletes fields. No ISO/Firestore Timestamp mixture on the wire.

TripSnapshot:

```text
schemaVersion: 1
rideId, riderId: string
driverId?: string                         assigned only after acceptance
status: searching|accepted|arrived|in_progress|completed|cancelled|no_driver_found
version: integer >= 1
pickup, dropoff: {lat: number, lng: number, address: string}
currentOfferId?: string                   searching only; not an accepted assignment
createdAt, updatedAt, searchDeadlineAt: epoch ms
acceptedAt?, arrivedAt?, startedAt?, completedAt?, endedAt?: epoch ms
cancellation?: {actorId: string, actorRole: rider|driver, reasonCode: string, at: epoch ms}
failure?: {code: no_driver_found, at: epoch ms}
```

OfferSnapshot:

```text
schemaVersion: 1
offerId, rideId, driverId: string
status: pending|accepted|rejected|expired|withdrawn
createdAt, expiresAt: epoch ms
resolvedAt?: epoch ms
rideVersion: integer                      version after offer's last aggregate change
pickup, dropoff: {lat, lng, address}       minimum driver display data; no rider UID/contact
```

The rider sees its trip and assigned driver's participant-safe display/location projection after acceptance. A pending offered driver reads only its own offer, not the full trip/rider identity. An accepted driver reads its assigned trip and terminal history. FCM tokens, eligibility evidence, receipts, and work records are never participant snapshots. Driver profile display fields are a separate read projection, not client-editable trip authority.

Live position has the exact projection fields in section 5b, including publisherGeneration, per-generation sequence and fixed freshness deadlines; it is separate from the trip version and cannot change status. Stale positions show freshness rather than simulated movement. ETA/route and approaching-destination UI are derived presentation data, not v1 lifecycle transitions.

## 4. Lifecycle and transition ownership

All guards are checked by backend inside atomic boundary. Every successful row increments version, updates updatedAt, records receipt/work, and emits a saved snapshot/offer to authorized observers. Invalid state, wrong actor, stale version, or stale identity has no partial effects.

| Operation | Initiator / permitted current state | Extra guards | Persisted result / observers |
| --- | --- | --- | --- |
| requestRide | authenticated rider / no active ride | valid locations; fresh commandId | searching v1; rider pointer; createdAt/searchDeadlineAt; dispatch work; rider observes |
| issueOffer (internal) | dispatcher / searching | before search deadline; no pending offer; eligible fresh available driver; not previously attempted for this ride | pending offer with deadline; reservation + current-offer pointer; trip stays searching; rider/driver receive their views |
| acceptOffer | exact offered driver / searching + pending offer | matching offerId/rideId/reservation; before expiresAt and searchDeadlineAt; expectedVersion | offer accepted; trip accepted, driverId/acceptedAt; reservation becomes on_trip; currentOfferId/current-offer pointer cleared; both participants observe |
| rejectOffer | exact offered driver / searching + pending offer | matching IDs/reservation; before expiry; expectedVersion | offer rejected/resolvedAt; release matching reservation and offer pointers; trip searching; dispatch work; rider/driver observe |
| expireOffer (internal) | scheduler / searching + pending offer | server now >= expiresAt | offer expired; release matching reservation/pointers; searching and dispatch work or no_driver_found if search deadline passed |
| withdrawOffer (internal) | backend on driver offline / searching + pending offer | matching reservation | withdrawn, release; dispatch retry; never cancel an accepted trip |
| arriveAtPickup | assigned driver / accepted | expectedVersion, same driver assignment | arrived + arrivedAt; both observe |
| startRide | assigned driver / arrived | expectedVersion, same assignment | in_progress + startedAt; both observe |
| completeRide | assigned driver / in_progress | expectedVersion, same assignment | completed + completedAt/endedAt; terminal handling below; both observe |
| cancelRide | rider / searching, accepted, arrived; assigned driver / accepted, arrived | expectedVersion, allowed reason | cancelled + cancellation/endedAt; pending offer withdrawn; terminal handling; both affected participants observe |
| exhaustSearch (internal) | scheduler / searching | now >= searchDeadlineAt; resolve/withdraw any pending offer | no_driver_found + failure/endedAt; terminal handling; rider and offered driver observe |

Terminal states are immutable. No completed→arrived, cancelled→accepted, arrived→searching, or in_progress cancellation in v1. Driver pre-pickup cancellation ends the ride; automatic reassignment after acceptance is excluded. Interrupted in-progress rides follow approved O01–O06 in section 10: preserve state/occupancy, contact participants and escalate; no silent completion/release or operator mutation. A separately reviewed/tested safe recovery path and staffed support remain mandatory pilot blockers. Same-command retries replay the receipt before checking current version. A new command repeating an already-achieved transition gets invalid_transition, not a second transition.

Offer rejection/expiry is not a trip status. `pending`, `driver_offered`, `driver_rejected`, `driver_accepted`, `in_transit`, en-route, and approaching-destination are not v1 wire statuses. Accepted is also the en-route-to-pickup phase.

Callable names (new v1 namespace; legacy requestRideFunction not silently repurposed):

| Callable | Request beyond common envelope | Success payload |
| --- | --- | --- |
| requestRideV1 | pickup, dropoff | CommandResult with trip |
| acceptOfferV1, rejectOfferV1 | rideId, offerId, expectedVersion | CommandResult with permitted trip or offer view |
| arriveAtPickupV1, startRideV1, completeRideV1 | rideId, expectedVersion | CommandResult with trip |
| cancelRideV1 | rideId, expectedVersion, reasonCode | CommandResult with trip |
| restoreSessionV1 | schemaVersion, required sessionRole: rider\|driver; no commandId | role-echoed RestoreSnapshot (section 5a) |
| getRideV1 | schemaVersion, rideId | participant TripSnapshot from live or history |
| listRideHistoryV1 | schemaVersion, actorRole, cursor?, limit? (section 5c) | RideHistoryPage, archive-only role-filtered descending keyset page |
| setDriverOnlineV1 | schemaVersion, commandId, online boolean (section 5c) | DriverOnlineResult with immutable historical committed result |

Mutation common envelope: `{schemaVersion: 1, commandId: UUIDv7}`. All trip/offer mutations except request additionally require exact positive integer expectedVersion; driver online control does not take a ride version. Do not accept client riderId/driverId/actorRole/status/timestamps in mutations. Payloads are allowlisted, IDs bounded to 128 characters, request body bounded, reasons enumerated. Approved reasons: rider_changed_plans, rider_requested_cancel, driver_unavailable; enforce role-appropriate values.

CommandResult: `{schemaVersion:1, commandId, rideId?, appliedVersion?, replayed:boolean, trip?:TripSnapshot, offer?:OfferSnapshot, serverTime}`. Return only the caller's permitted view; rejected driver receives resolved offer, not full trip. Replayed result preserves original business result, rideId, version, and timestamps; replayed/serverTime metadata may differ. A response may be older than already-observed stream data; client never regresses versions.

Receipt key `(authenticated uid, commandId)`; fingerprint includes operation, schema and full normalized payload. Same key + different fingerprint rejects command_id_reused. Same key + same fingerprint returns original committed success even after later transitions/archival. Full receipts/results are retained 30 days; no lifetime tombstones. Look up receipts first. Without a receipt, the UUIDv7 embedded creation time must be at most 24 hours old and at most 5 minutes in the future against backend time, otherwise reject receipt_expired/command_clock_skew without executing. A pruned old ID is therefore permanently inadmissible. Apps compensate clock skew using restore serverTime, persist the exact ID before sending, and never rewrite IDs or automatically mint replacement actions to bypass expiry. Clients stop automatic retries after 24 hours and reconcile session/history before deciding on a genuinely new action. Failed preconditions are not successful receipts; clients reconcile before choosing a new intended action. Privacy-driven receipt deletion cannot make expired IDs executable.

Typed failure details: `{schemaVersion:1, reason, retryable:boolean, rideId?, currentVersion?}` with callable codes: unauthenticated; permission-denied (wrong participant/eligibility); invalid-argument (malformed/schema/command_id_reused/command_clock_skew); failed-precondition (active_ride_exists, invalid_transition, offer_expired, stale_offer, unsupported_version, receipt_expired); aborted (version_conflict); unavailable/internal (transient). Only authorized participants receive ride/version details. Active-ride-exists provides own active rideId for restoration. Transient/lost response retries use same commandId, never mint a replacement request.

RestoreSnapshot is the role-discriminated shape in section 5a. Terminal reference is per role, may coexist with a newer active trip, and must never replace that active trip in UI.

## 5a. C01 role-scoped sessions and cross-role admission

C01 policy is user-approved in section 10; it remains unimplemented. C02 telemetry semantics are specified in section 5b; C03 online/history result envelopes are specified in section 5c. Named staffing, recovery, capacity and runtime/pilot gates remain unfulfilled.

`SessionRole = rider|driver`. Restore authenticates UID; sessionRole selects an owner projection and never grants eligibility. Missing, null or unknown sessionRole returns callable invalid-argument with `{schemaVersion:1,reason:"invalid_session_role",retryable:false}`. Unknown fields are rejected. No commandId is accepted. Restore remains available to authenticated ineligible/revoked drivers to discover retained own assignment and history; new driver mutations still require trusted eligibility.

Exact success shapes (optional fields are omitted, never fabricated):

```text
RiderRestore = {schemaVersion:1, sessionRole:"rider", serverTime,
  activeTrip?:TripSnapshot, lastTerminal?:TerminalReference,
  blockedByRole?:"driver"}
DriverRestore = {schemaVersion:1, sessionRole:"driver", serverTime,
  activeTrip?:TripSnapshot, pendingOffer?:OfferSnapshot,
  lastTerminal?:TerminalReference,
  effectiveDriverAvailability:"offline"|"available"|"reserved"|"on_trip",
  blockedByRole?:"rider"}
TerminalReference = {rideId:string, version:integer>=1, endedAt:epoch-ms}
```

Rider activeTrip comes only from validated own riderActive pointing to a nonterminal trip whose riderId is UID. Rider response never contains pendingOffer or effectiveDriverAvailability. Driver activeTrip comes only from own on_trip assignment and matching accepted/arrived/in_progress trip whose driverId is UID. Reserved assignment yields only pendingOffer, validated against own current-offer pointer, pending offer and searching trip; driver restore never returns a searching trip. Driver activeTrip and pendingOffer are mutually exclusive. lastTerminal comes only from selected role's pointer even if the opposite role has a newer terminal; it may coexist with selected-role activeTrip/pendingOffer or blockedByRole.

blockedByRole is required exactly when the opposite role occupies the UID; selected-role activeTrip/pendingOffer must then be absent. It exposes no opposite-role rideId, offerId or snapshot. The other app can explicitly restore its own role. Online intent may stay true during a rider trip, but driver restore reports offline plus blockedByRole:rider and dispatch excludes it. Completion does not force online intent true; availability is recalculated from existing controls/freshness. Same-role devices restore the same resource; there is no per-device business slot.

Restore reads relevant trip_state state coherently and validates associations. Dangling active pointers, simultaneous cross-role occupancy, self-assignment, mismatched/missing offer or assignment, or terminal records still occupying active pointers return callable failed-precondition with `{schemaVersion:1,reason:"reconciliation_required",retryable:false}` and no success snapshot. Do not clear resources or guess idle/completed. Preserve known client identity as stale, disable new business mutations, retry restore after reconnect or explicit refresh, and escalate persistent inconsistency operationally. A missing lastTerminal live record is normal: fetch through getRideV1 history fallback; if both are absent surface explicit unavailable/not-found, never invent completion. Restore returns a role-scoped terminal reference without embedding it. No unauthorized identity is included in errors.

Admission uses the same /trip_state transaction as resources/receipts/work, after receipt-first replay and authentication/input validation:

| Action | Atomic C01 condition and outcome |
| --- | --- |
| new requestRideV1 | Valid own riderActive: failed-precondition active_ride_exists with own rideId. Otherwise driverAssignment reserved/on_trip: failed-precondition cross_role_busy without rideId. Neither changes resources. If neither exists, create rider trip/pointer. |
| candidate selection and issueOffer claim | Exclude candidate UID == riderId and candidate riderActive at filtering AND transaction claim; require no driverAssignment plus existing eligibility/online/freshness guards. Lost race skips candidate and continues bounded search; never steals/releases occupancy. |
| acceptOfferV1 | Also require offer.driverId != trip.riderId and no riderActive for driver. Self-match returns permission-denied self_match_forbidden; opposite-role occupancy returns failed-precondition cross_role_busy. No partial effects or release. |
| online command | Acquires no business slot; cannot clear riderActive or accepted assignment. online=true during rider occupancy may set intent but effective availability stays offline. Existing offline withdrawal stays unchanged; response/replay semantics are in section 5c. |
| new mutation in corrupt state | failed-precondition reconciliation_required before resource changes; internal dispatch skips affected state and signals operations. No automatic repair is defined. |

C01 failures use existing details `{schemaVersion:1,reason,retryable,rideId?,currentVersion?}`. cross_role_busy, self_match_forbidden and reconciliation_required have retryable:false. On accept, a validated self-match takes precedence over cross_role_busy; other inconsistent associations use reconciliation_required. For valid state, receipt-first exact successful retry returns its original result even if UID now occupies the opposite role; it does not reacquire or clear any slot. Changed operation/payload stays command_id_reused. Failed preconditions do not create successful receipts.

Request versus dispatch on one UID has two serial outcomes: request commits riderActive first and reservation cannot commit, or reservation commits first and request fails cross_role_busy. Distinct same-role request commands admit one and reject the other active_ride_exists; competing driver claims admit one reservation. Release-versus-admission follows transaction order: new admission succeeds only after exact prior occupancy is released. Delayed terminal cleanup cannot remove the new resource. Self-candidates never win. Role switch/login/heartbeat/notification never implicitly cancels, withdraws or reassigns the other role's resource.

Terminal commit writes lastTerminal/{riderId}/rider and, only when an accepted driver exists, lastTerminal/{driverId}/driver. Offer-only drivers acquire no participant history. listRideHistoryV1 actorRole is required rider|driver: rider filters immutable riderId == UID; driver filters immutable driverId == UID. Role selection never grants membership or eligibility. Sequential trips in different roles remain separate rideId documents and terminal pointers. Terminal/replay/cleanup touches only matching identities in original roles and cannot clear a later opposite-role occupancy.

## 5b. C02 telemetry ingestion, sessions and freshness

C02 semantics and transport/freshness defaults are user-approved in section 10. C03 online/history envelopes are complete in section 5c. Use authenticated Firebase HTTPS callables, not direct client database writes. These calls have their own TelemetrySession/TelemetryAck envelopes, not lifecycle CommandResult or its UUIDv7 receipts. No operation here changes eligibility, onlineIntent, assignment, reservation, trip phase or ride version.

### Transport and private storage

All requests require schemaVersion:1 and sessionRole:"driver"; auth UID is the only driver identity. Reject unknown fields, client UID/rideId/status/timestamps claiming server authority, invalid enums and bodies >8192 UTF-8 bytes. Session/acquisition/publisher IDs are UUIDv4 strings; generation and sequence are positive safe integers <=9007199254740991, except expectedGeneration may be zero. Coordinates are finite WGS84 named lat/lng (zero valid). Accuracy is required finite accuracyMeters in [0,10000]; capturedAt is integer epoch ms estimated against server time. FCM token is optional bounded string 1..4096 bytes or explicit null to clear; omission retains existing token. It is private and not required for telemetry, offers or restore.

Server-only RTDB /driver_presence/{uid} contains current generation (retained monotonic high-water mark), publisherId, sessionId, acquisitionId/fingerprint, active flag, lastSequence (zero before first sample), lastSampleFingerprint, lastAck, latest accepted sample, private token and lastClosedSession. Session acquisition and upload transact at this per-UID boundary. The generation high-water mark must not be reset/pruned while UID exists; account deletion disables old authentication before removing it. Session replacement clears latest sample/lastAck/sequence and invalidates presence immediately; it does not change token or online intent. No raw telemetry/session/token field is included in trip snapshots.

Eligibility is read from trusted driverControl immediately before each call; ineligible returns permission-denied driver_ineligible. This read races administrative changes outside the presence boundary: an already-authorized in-flight call can finish after revocation. It cannot create eligibility or assignments; dispatch and projection recheck authoritative eligibility. Driver-role metadata is not evidence of eligibility. Revoked owners can still restore retained trips via C01, but cannot acquire/upload. Authentication/session/shape checks occur even for duplicate telemetry.

Exact operations (request fields after common schemaVersion/sessionRole):

| Callable | Allowlisted request | Success |
| --- | --- | --- |
| beginDriverTelemetrySessionV1, action inspect | action:"inspect", publisherId | {schemaVersion:1,serverTime,currentGeneration,matchesPublisher:boolean}; currentGeneration:0 if absent. No sessionId/token disclosure or mutation |
| beginDriverTelemetrySessionV1, action acquire | action:"acquire", publisherId, acquisitionId, expectedGeneration | TelemetrySession |
| beginDriverTelemetrySessionV1, action resume | action:"resume", publisherId, sessionId, generation | TelemetrySession |
| closeDriverTelemetrySessionV1 | publisherId, sessionId, generation | {schemaVersion:1,serverTime,sessionId,generation,closed:true}; repeats of exact lastClosedSession return same closed identity without affecting newer sessions |
| uploadDriverTelemetryV1 | publisherId, sessionId, generation, sequence, capturedAt, lat, lng, accuracyMeters, fcmToken? | TelemetryAck |

TelemetrySession = {schemaVersion:1,serverTime,publisherId,sessionId,generation,lastAcceptedSequence,nextSequence,replayed:boolean}. nextSequence = lastAcceptedSequence+1, except at maximum sequence it is omitted and sequenceExhausted:true is required (otherwise sequenceExhausted is omitted). Session has no idle expiry; freshness separately expires. Session generation maximum fails session_generation_exhausted and requires operational resolution, never wraps.

TelemetryAck = {schemaVersion:1,serverTime,publisherId,sessionId,generation,sequence,outcome:"accepted"|"duplicate",acceptedAt,capturedAt,locationValidUntil,heartbeatValidUntil}. All times integer server epoch ms except capturedAt is echoed untrusted input. acceptedAt is fixed backend receipt time of original commit; serverTime may change on duplicate. Both validity deadlines are fixed by original commit. No ride/assignment/online-success claim appears in the ack.

Canonical fingerprints include operation and every allowlisted request field, with sorted field names, finite numeric values normalized consistently (including -0 to 0), and no whitespace/key-order significance. Omitted fcmToken, explicit null and a string are three distinct token operations. A request never gains fingerprint equality by dropping a supplied field. Invalid/malformed requests fail before fingerprint comparison.

### Acquisition, recovery and fencing

One active publisher per UID. Each installation generates and persists publisherId; acquire intent stores exact acquisitionId/expectedGeneration before sending. Inspect obtains currentGeneration; first acquire uses zero. Acquire transaction first recognizes exact current acquisitionId+publisherId+expectedGeneration fingerprint: if still active, return same TelemetrySession replayed:true without resetting sequence/freshness. Same acquisitionId on current record with changed payload fails acquisition_id_reused. Otherwise expectedGeneration must equal retained high-water mark, then allocate generation+1 and a new server-random sessionId generated before transaction. This explicit CAS acquisition is takeover; two devices using the same expectedGeneration have one winner. The loser fails session_generation_conflict and must inspect and require an explicit publisher-start/takeover user decision, not automatically increment/retry. An acquisition from an older generation can never reactivate itself: superseded acquisition retry has stale expectedGeneration and fails. No historical acquisition receipt bypasses the CAS.

Resume requires exact current active publisherId/sessionId/generation, returns current lastAcceptedSequence without increment or freshness refresh. After restart, resume the persisted session or retry the exact persisted unacknowledged acquisition intent; never automatically acquire a replacement merely because a response was lost. If no saved session exists, inspect and a new explicit publisher start are required. A different device has a different publisherId and cannot resume the existing publisher. Losing publisher receives stale_telemetry_session on upload/resume. Close compares exact current identity, records lastClosedSession, marks inactive and clears latest sample; generation remains high-water mark. Exact lastClosedSession replay is harmless even after later acquire; other stale close fails and cannot close newer publisher.

Offline intent and session ownership are independent. Normal driver offline/logout stops local publishing and attempts close if network/auth allow; an offline command itself need not close the session or erase assignment. A lost close leaves no continuing local heartbeat and presence becomes stale. Authentication revocation rejects subsequent calls; logout cannot retroactively revoke a call already authenticated. Foreground/permission recovery resumes exact saved session and collects fresh GPS; permission denial never fabricates a heartbeat or online success.

### Samples, sequence, delayed capture and retries

Each active session starts sequence 1. Upload transaction checks current active publisher/session/generation and lastSequence atomically with sample storage. sequence > lastSequence accepts (gaps allowed), sequence == lastSequence with identical normalized entire sample payload including token operation is duplicate, changed payload fails sequence_reused, and sequence < lastSequence fails out_of_order_sample. Only the latest successful ack/fingerprint is retained; replay older than latest gets out_of_order_sample, never heartbeat refresh. At maximum sequence, no next upload is admissible; explicit inspect/acquire starts a new fenced session. Replacement/close and sample acceptance serialize at same boundary: old upload either commits before replacement or fails after it, never writes a newer session.

Use backend transaction-attempt time T as acceptedAt for a new sample. Approved bounds: capture age C=10000ms, future allowance F=2000ms, receipt heartbeat H=30000ms. Accept only T-C <= capturedAt <= T+F (inclusive); older fails sample_too_old, future fails sample_clock_skew. Recheck on every retry of transaction callback. These untrusted timestamps only bound honest-client transport delay; server cannot prove actual GPS capture time/location or prevent a malicious authenticated publisher inventing them. OS cached fixes must retain original capture time, never relabel upload time as capture. Token update is atomic only with an accepted sample. Duplicate resolution checks fingerprint before capture-age validation and returns original ack even if now old, without updating sample, token, receipt or deadlines.

Set locationValidUntil=min(T+H,capturedAt+C), heartbeatValidUntil=T+H. A received-liveness heartbeat exists only for a newly accepted location sample; there is no separate heartbeat-only endpoint. ### Projection and access ordering

Exact participant projection at /trip_locations/{rideId}: {schemaVersion:1,rideId,driverId,publisherGeneration,sequence,lat,lng,accuracyMeters,capturedAt,serverReceivedAt,locationValidUntil}. publisherGeneration is the per-UID generation, not ride.version; sequence compares only within one generation. No publisherId/sessionId/token/acquisition identity is public. Order by (publisherGeneration,sequence) lexicographically for a fixed driverId/rideId; compare IDs before ordering. A replaced publisher's low sequence can supersede older generation; a lower generation never supersedes it.

Projection work reads latest sample and performs a conditional Admin SDK transaction at RTDB root / that checks source generation/sequence is still current/active and fresh, driverControl eligible, exact driverAssignment kind:on_trip/rideId, corresponding trip.driverId and accepted/arrived/in_progress status, and destination order. Only a strictly greater ordering tuple writes; exact tuple repeat is no-op and must not refresh timestamps. It copies original acceptedAt as serverReceivedAt and original locationValidUntil. Rechecking outside that transaction then writing is forbidden. This root projection transaction is a deliberate separate contention boundary, required for atomic source+association+destination fencing; it changes only /trip_locations and never copies GPS into /trip_state. The F02 feasibility benchmark MUST include this bounded projection workload, root conflicts with lifecycle/presence and pilot-rate admission; no supported capacity is asserted. If unsuitable, redesign/re-review projection before implementation rather than weakening fences.

Projection processing coalesces to the latest stored sample per UID, with approved at-most-one publication attempt per driver per 5s. Presence-change triggers enqueue a hint; periodic bounded reconciliation inspects active assignments/latest presence so a lost hint cannot permanently strand tracking. Retry rereads latest state rather than retaining old GPS as a new sample. Final scan/driver-count/rate limits must be recorded by F02; the 5s cadence is advisory during outage and cannot extend a freshness deadline. Transaction callbacks have no external side effects.

Source acceptance/session takeover and terminal association change can therefore serialize with projection: an old job cannot overwrite a newer valid tuple, change ride association or commit after its source is superseded. A projection written before takeover may remain visibly stale until fresh data/deletion, but its deadline never extends. Terminal state immediately revokes reads through authoritative trip participant/status rules even before deletion. Cleanup also uses exact rideId/driverId/generation/sequence conditional identity and cannot delete newer data. Reads never trust projection claims; current trip participant membership and status authorize, with no parent/public grant. Telemetry/projection writes, session state and private tokens are server-only; owner clients get only callable responses. On stale/deleted/denied projection, stop tracking/present freshness without altering trip phase.

## 5c. C03 online intent and terminal history pages

C03 wire semantics are complete and their product defaults are user-approved in section 10; implementation and pilot gates remain separate. All C01/C02 invariants remain. The two result types below are separate from trip CommandResult and telemetry envelopes.

### Online request, transaction, receipt and observation

Exact request: {schemaVersion:1,commandId:UUIDv7,online:boolean}. Every field is required, unknown fields and null/nonboolean online are invalid. Existing commandId bounds/fingerprint/clock admission/receipt retention apply; maximum body 8192 UTF-8 bytes. No sessionRole, UID, expectedVersion, availability or trip identity is accepted. Operation/authenticated UID determine driver context. Validate schema/payload/auth first, then look up own receipt before new-command eligibility/version/resource guards. Exact successful receipt replay is a read of the caller's original result, allowed after eligibility revocation; it grants no new mutation privilege. Changed payload/operation remains command_id_reused. Only a new command requires trusted driverControl.eligible:true; client profile.role is irrelevant.

Extend server-owned /trip_state/driverControl/{uid} with onlineRevision (safe integer 0..9007199254740991) and onlineChangedAt? (backend epoch ms). A missing control record is initial offline/revision 0/no changedAt and not eligible. A valid pre-C03 proposed record lacking revision/time normalizes its existing boolean onlineIntent as baseline revision 0/no changedAt; this is interface compatibility, not permission to fabricate a persisted intent. Revision 0 has no onlineChangedAt; positive revision requires it. Other malformed combinations require reconciliation_required, never guessed repair. Actual boolean intent change increments revision once, stamps onlineChangedAt and changes onlineIntent inside /trip_state transaction with receipt/effects/work. A fresh-ID same-intent no-op succeeds with intentChanged:false, existing revision/onlineChangedAt unchanged, and a new receipt committedAt; no ride version changes or repeated side effects. Revision counts only onlineIntent transitions, not eligibility, heartbeat, reservation or trip changes. It never wraps; a change at max fails online_revision_exhausted. Every set onlineIntent writer must preserve this rule; eligibility administrative updates preserve online fields.

online=false atomically withdraws only the exact current pending offer/reservation if present, resolves offer status:withdrawn/resolvedAt, increments its searching ride aggregate version once, clears only matching current-offer/assignment pointers and creates dispatch work, in the same transaction as control/receipt. Return limited resolved own OfferSnapshot as withdrawnOffer, never full unassigned rider trip. A valid on_trip assignment is preserved. online=true may retain intent while rider-active, but effective availability remains offline. Consistent same-intent no-op has no reservation to withdraw when already offline; contradictory pointer/control state returns reconciliation_required instead of a success/no-op. No GPS/token/session/freshness refresh occurs.

### History request, page and order

Exact listRideHistoryV1 request: {schemaVersion:1,actorRole:"rider"|"driver",limit?:integer,cursor?:string}. No commandId/UID/sessionRole/status/filter/sort fields. Unknown fields, null cursor/limit, invalid role or noninteger limit reject. Absent cursor starts a new traversal; first-page absent limit defaults to 20; valid inclusive range is 1..50. On cursor requests absent limit inherits that cursor's fixed limit; explicit different limit rejects without silently starting page one. A cursor is 43 base64url characters (256 random bits), maximum 43 bytes, not client-decodable state.

RideHistoryPage = {schemaVersion:1,actorRole:"rider"|"driver",serverTime:epoch-ms,
  items:TripSnapshot[],hasMore:boolean,nextCursor?:string}
All fields except nextCursor are required. nextCursor is present exactly when hasMore:true, otherwise omitted (not null). Empty result is items:[],hasMore:false with no cursor; no error and no claimed globally complete history. Every item is supported schemaVersion:1 and terminal completed|cancelled|no_driver_found, full immutable TripSnapshot. Rider filter is riderId==auth UID; driver filter is immutable assigned driverId==auth UID; offer-only drivers get no item. Missing driverId is valid for unassigned terminal trips and excluded from driver pages. Eligibility revocation does not deny own participant history. Legacy unsupported records are excluded by schemaVersion query; overwritten legacy trips cannot be reconstructed. Unexpected corrupt/nonterminal purported v1 archive documents cause history_data_invalid, not fabricated partial items.

Read Firestore /rides only, not merged RTDB terminal state. Query own participant field and schemaVersion:1, endedAt<=traversalUpperBound, orderBy endedAt DESC then document ID (__name__) DESC. All collection IDs share the rides prefix; tie-break follows Firestore document-name byte ordering, not locale, timestamp insertion order or client sorting. Implementation records required participant/schema/endedAt/document-name composite indexes before release. Fetch limit+1 qualifying records in one query: return first limit, hasMore iff extra record existed in that query; if true create next cursor after last returned tuple. Keyset next page is strictly after that tuple in descending order: endedAt smaller, or equal endedAt with strictly smaller document name. Boundary is exclusive; deleting boundary document does not invalidate stored tuple.

### Archive consistency and client recovery

Pagination is best-effort over archive state at each page query, not a cross-page snapshot or RTDB/Firestore transaction. Upper bound excludes terminal endedAt newer than traversal start; refresh starts a new upper bound. A late archive with endedAt<=upper bound can insert anywhere: one newer than/equal to an already consumed key can be missed until refresh; one after the current exclusive boundary can appear on a later page if archived before that query. Equal-endedAt insertions obey document-name tie order, so a new ID ahead of boundary is missed and one behind can appear. An older archive inserted after its key range was consumed or after hasMore:false is also missed until refresh. No traversal guarantees completeness while archive is still changing. A successful empty/last page means no extra row was visible to that bounded query, not no trip/terminal state.

Page retries can return newly inserted/deleted rows and a different hasMore. Retention/deletion can remove previously returned items or shorten a page; immutable surviving trips never change order/timestamps. UI retains/de-duplicates already loaded terminal items by rideId/version within traversal and may show refreshed/deleted data only under explicit refresh policy; it never infers completion from disappearance. Fresh page-one refresh replaces traversal/cache after successful response and invalidates old cursors/callbacks; refresh may still omit archives not yet written. Known terminal recovery uses selected-role lastTerminal and getRideV1 live/history fallback regardless of listing being empty or archive unavailable. No endpoint invents missing legacy history or claims archive completeness.

### Approved history retention boundary

Apply R03 in addition to the pagination query: at query/read backend time N, an ordinary archived terminal is readable only while N < endedAt + 90 days. Thus each page excludes endedAt <= N - 90 days as well as enforcing its original traversal upper bound/exclusive cursor boundary; the lower retention boundary may advance between pages. Cursor retries cannot extend access. Direct participant document reads and getRideV1 archive fallback enforce the same ordinary-history deadline, even if physical TTL deletion lags. R02's never-archived sole-live safety exception is distinct from ordinary archived history. Retention deletion/late archive nonresurrection follows section 7; immutable surviving snapshots and wire envelopes remain unchanged.

## 6. Matching, durable work, and races

Approved defaults: 120s overall search, 20s per offer, 5s retry cadence, 30s maximum presence age, one attempt per driver per ride. Offer expiry <= search deadline. Driver ranking uses distance within the approved 5km radius; zero/boundary coordinates and neighboring geohashes must work. No eligible candidates means keep searching until deadline, then no_driver_found. Every retry rechecks authoritative ride/version/reservation; cancellation/acceptance wins if already committed. Accept at/after deadline rejects; transaction ordering determines cancel-versus-accept winner, later operation sees updated state.

Work records are committed with transition and processed at least once. Workers claim bounded leases with fencing tokens; only the current lease may acknowledge work. Use deterministic workId + guarded state/offer identity, retry transient failures with capped backoff, and periodically reconcile overdue searches/offers/archive jobs. Transaction callbacks perform no external calls or ID generation; generate IDs beforehand and recheck backend time/deadlines on each attempt. Worker restarts cannot lose a committed intent. FCM is best-effort hint `{type, schemaVersion:'1', rideId, offerId?, version}` as strings; app fetches/subscribes to saved authorized state. Missing token/send error cannot extend offer validity. Cleanup may lag deadlines during outages, but expired offers cannot be accepted, and reconciliation releases their reservations after service recovery; do not promise wall-clock cleanup while workers are unavailable. Persist offer before send; duplicated sends open one offer UI keyed by offerId. Driver restore/stream discovers missed offers.

## 7. Terminal handling, archive, and recovery

Terminal commit atomically freezes trip, ends any pending offer, clears rider/driver/current-offer pointers only if they still match this ride/offer, writes lastTerminal references and archive work, and releases reservation. A released driver becomes available only if online intent and freshness permit. Never clear a newer ride's pointers during retry. A terminal trip may remain in the live rides map but no longer blocks a new trip.

Archive worker writes immutable Firestore rides/{rideId} idempotently with exact terminal version and timestamps. Replays cannot overwrite a different identity/version or replace terminal business timestamps with archive time. History allows rider and accepted driver read only. Offer-only drivers retain limited resolved offer view during its retention.

Approved retention R01–R15 is specified in section 10 and the decision registry. Live terminal remains at least 24h from endedAt AND until archive acknowledgement; cleanup checks both and exact identity. Archive failure retains sole live data/work and raises incident without blocking a new trip. Ordinary Firestore history expires 90d from endedAt, committed receipts/results 30d from original commit, closed offers 24h from resolvedAt and role-specific lastTerminal 30d from endedAt (new terminal may replace it). Expiry restricts reads/query results even before physical deletion; receipts and other permitted copies follow their own category.

Late/retried archive work must not recreate ordinary history at/after endedAt+90d. If prior archive acknowledgement exists, finish identity-conditional live/work cleanup without reinserting expired history. If the sole live terminal was never archived/acknowledged, retain it and unfinished work as R02's monitored safety exception; do not invent acknowledgement or delete sole recovery evidence. Escalation/resolution follows the separately reviewed recovery/runbook gate; no new operator mutation is created here. Expired/absent history can yield explicit unavailable/not-found; it never authorizes invented completion.

Raw coordinate-bearing latest presence/projection expires at acceptedAt+30 minutes, or earlier conditional close/replacement/terminal cleanup. Keep minimal latest ack, digest and sequence/generation metadata for C02 exact duplicate/fencing behavior; cleanup cannot reset fences, refresh deadlines or republish expired GPS. An authorized nonterminal participant may still read/display stale projection until cleanup; staleness forbids using it as fresh tracking, while terminal state revokes reads immediately.

watchRide first attaches live listener and resolves getRide/history as needed; on absent/deleted live value fetch history, preserving last known state. Absence is not completion, cancellation, or idle. If neither exists return explicit not-found/unavailable observation and reconcile restoreSession; never invent terminal state. Ignore lower versions, distinguish schema failure from connection failure, use last known snapshot with stale/reconnecting indication, and unsubscribe on logout/ride replacement/disposal. Login restores from server, not local BLoC state. Offline commands requiring network stay pending/disabled; do not optimistically advance business lifecycle.

## 8. Authorization and trust boundaries

No client writes under trip_state or Firestore rides. Participant reads are per-record and do not grant list-all access. Rider reads own active pointer/trips, assigned driver reads its trip, driver reads own assignment/current offer, owner reads own lastTerminal. Offer-only driver reads only own offer projection. Backend may read all for dispatch; clients never gain that permission. Server-only receipts/work. Do not store private server fields inside a client-readable parent because RTDB parent grants expose descendants.

Driver eligibility is the server-only driverControl.eligible record, never mutable profile.role. Driver mutations require trusted eligibility; revocation preserves an existing assignment for explicit operational resolution rather than silently releasing it. Ordinary profile updates allowlist personal fields and forbid role/approval/participant IDs. Presence owner uses the section 5b authenticated callable transport; only the server writes session/presence state, stamps accepted receipt time and enforces fenced sequence/freshness rules. Online intent changes only through setDriverOnlineV1. Clients cannot write eligibility, assignment, or trip_locations. Token fields are owner/server only. Server projects only the section 5b allowlisted participant fields to /trip_locations/{rideId} with atomic publisher/association/order fencing. Read permission checks current trip_state participant identity and accepted/arrived/in_progress status, not the projection's claims. Terminal state immediately revokes location reads even if projection deletion lags. Projection work rechecks association; clients reject mismatched IDs. No public driver-location parent grants.

Firestore history has no direct client collection listing in v1: getRideV1/listRideHistoryV1 authenticate and apply riderId/driverId filters server-side with bounded pagination. Direct single-document reads may be participant-authorized, with no client write/list grant. Backend query indexes are recorded during implementation planning. Abuse limits/schema validation apply to commands/telemetry. Rules deny default and tests cover delete/parent-write/list bypasses.

SessionRole supplies actorRole; no client-selected foreign UID/filter exists. Refresh creates a new traversalId immediately, invalidating old in-flight page callbacks/cursors for application, while retaining previously displayed same-role items as stale until successful new page one replaces them. Failed refresh preserves those items with a retry indication; successful empty page replaces the history list with an explicit empty archive result, never activeTrip or terminal recovery state. Account/role change clears visible foreign-context items and invalidates callbacks. No stale next-page response from a prior traversal can append after refresh.

Coalesce duplicate load-next for the same traversal/cursor into one unresolved request. Transient failure retries exact cursor/limit presence; after success advance only to the returned nextCursor. Repeating a previous read due to uncertainty may return different archive rows/token: merge validated terminal items by rideId/version, retain already displayed items during traversal and order by section 5c's backend total order, never locale sorting. Conflicting same-ride immutable content is a protocol/data failure, not permission to invent a new version. hasMore:false ends this traversal only; do not claim complete lifetime history. Invalid/expired cursor stops pagination and requests explicit refresh; it never silently fetches page one. Keep cursor opaque/private to its UID/role/traversal and avoid displaying/logging it in UI. A limit change is a new explicit traversal, not mutation of a cursor request.

Archive lag, newer/tied/older concurrent insertions and deletion follow section 5c's best-effort model. An empty/failed list does not remove known lastTerminal, imply ride completion or replace an active trip. Selected-role terminal recovery still uses lastTerminal/getRideV1 regardless of list results. Refresh can reveal late archives, but cannot promise archives already exist. Loading-first, loading-next, loaded, empty, retryable failure and explicit-refresh-required are distinct accessible workflow states; widgets do not fetch during build or orchestrate pagination.

Future Freezed online/control/history/page/failure models belong in packages/ulendo_models; parsing, exact retries, revision reconciliation, traversal identity and UID/role caches belong in packages/ulendo_core. Each app's BLoC owns its history rendering workflow; driver BLoC owns online actions; repository streams coordinate shared observations without BLoC-to-BLoC dependencies. C01 role/occupancy/history semantics and C02 telemetry/freshness/publisher fences remain unchanged. C04 policies are approved and durable documents published in this working tree. Whole-contract review is a separate stage; runtime/capacity/operational and named pilot-staffing/recovery gates remain outstanding.
